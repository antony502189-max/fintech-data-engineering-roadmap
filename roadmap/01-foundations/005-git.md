# 005. Git, review, and reproducibility

## Learning outcome

Make a model change understandable to an independent reviewer.

## How it works

A commit connects a code snapshot to an explanation. Small substantive changes are easier to review, but commit count does not measure maturity. Reproduction also needs input versions, parameters, and the environment. Never alter dates to imply years of development.

## Fintech example

Fixing a refund filter changes last month's total. Review must cover the business effect, a meaningful test, and the historical rebuild plan.

## Implementation steps

1. Create a branch in your fork
2. Make the smallest useful change
3. Show fixture results before and after
4. Explain the affected rebuild scope in a PR.

## Practical assignment

Fix an intentionally incorrect net formula in a personal SQL copy. Add a test demonstrating the defect and document the changed totals.

## Common mistake and its consequences

Combining renaming, formula changes, and migrations makes the monetary effect difficult to inspect.

## Verify the result

A reviewer can identify the affected metric, period, and recovery method from the diff and description.

## Self-check question

What information beyond the commit SHA is needed to reproduce a financial report?
