# C06. Backup restore with an atomic checkpoint

**Level:** intermediate to advanced. **Time:** 2–5 hours. [Related material 1](../roadmap/08-reliability/077-backup.md) · [Related material 2](../roadmap/02-sql/015-transactions.md)

## Scenario and contract

Use real SQLite databases and the backup API. Each batch has immutable events [id,signed_minor], an end_seq, and optional crash_before_checkpoint. Start with checkpoint=0 and no events. Write accepted events and checkpoint in one transaction. Exact event repeats are safe; different amounts under one ID cause a conflict and stop subsequent batches.

Inject a single exception after row writes but before checkpoint update for a flagged eligible batch. Record a rolled_back attempt, then retry once without injection. Already committed end_seq values return skipped with one attempt. Trace each attempt using batch number, attempt number, status, checkpoint, sorted IDs, and total_minor.

Keep an initial backup; replace it after the requested 1-based backup_after batch if reached (0 means initial backup). Restore to a separate database and replay all source batches without injected crashes, stopping at conflicts. Return attempts, live state, restored state, and equal. State includes checkpoint,ids,total_minor.

## Hint

A nested helper that commits independently can break your data/checkpoint transaction. Take backups outside active transactions.

## Deliverables and review

A restoration trace, an actual backup operation, and proof that failed attempts never advance progress.

Keep the implementation, passing output, one failing counterexample, and a short note explaining the financial or operational consequence. Check the input contract rather than silently extending it. Synthetic fixtures do not establish production-scale or regulatory guarantees.
