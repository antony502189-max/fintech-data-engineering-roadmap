# C01. Multi-batch payments, replay, and rollback

**Level:** intermediate to advanced. **Time:** 2–5 hours. [Related material 1](../roadmap/02-sql/015-transactions.md) · [Related material 2](../roadmap/04-ingestion/039-replay.md)

## Scenario and contract

Implement `solve(data)` over `data["batches"]`, an ordered list of event batches using the core lab contract. Preserve database state across batches. Return a `steps` trace, sorted accepted `event_ids`, `posting_count`, and `quarantine_count`.

Each successful step contains status=committed, inserted/duplicates/quarantined counts, and the entire current daily view. A payload collision returns a step with only status=conflict and the unchanged daily view; continue with later batches. Schema defects quarantine per row. A conflict rolls back every new event and quarantine row in its batch. Postings must remain complete and balanced after every step. Daily order is event_date,currency.

Reuse the core lab functions if helpful. The challenge is to make the state transitions observable, including a valid insert immediately before a conflicting event.

## Hint

Do not recreate the database per batch. Check current state after the exception, not the partially attempted rows.

## Deliverables and review

A JSON trace plus a crash matrix explaining which transaction owns each write.

Keep the implementation, passing output, one failing counterexample, and a short note explaining the financial or operational consequence. Check the input contract rather than silently extending it. Synthetic fixtures do not establish production-scale or regulatory guarantees.
